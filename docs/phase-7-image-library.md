# Phase 7 — Image library and project organization

Review branch built on the Phase 6 commit. No production merge/deployment, hosted migration or paid provider test.

## Customer experience

`/app/library` consolidates authorized original uploads and saved generated outputs. It uses existing image, job, pack, batch and quality records; no copied image files or second history system. The workspace navigation links to the library. Grid/list views, accessible selection counts, select-loaded, move, rename, trash/restore, individual download links and project create/rename/archive/restore/delete are functional API operations. A project can be opened directly with `?project_id=...`; archived projects require the explicit archived filter. Search matches filenames and current project names case-insensitively as literal text, not SQL wildcards. Filters cover project/unassigned, role, mode, provider state, user decision, UTC date range and stable newest/oldest/filename sorting. All stored photo formats are WebP after existing normalization, clearly stated rather than presenting nonfunctional format choices.

Pages contain 24 records with an incremental Load more action; searches reset selection/offset, and stale responses cannot replace newer query results. Thumbnails are lazy-loaded through an authenticated private endpoint and bounded to 480 pixels per side. Full originals/results load only on explicit preview/download. The thumbnail endpoint verifies ownership, size and checksum before decoding, limits transforms to two active requests and a bounded 24-request waiting queue with a 15-second deadline. No public URL, API credential or filesystem object path is returned. Thumbnails are derived without permanent duplicate stored files and are private/no-store.

The preview dialog shows the selected full image on demand. Paginated related jobs link to the existing original/result comparison and quality-review page; all related generated versions remain actual job records. Pack links open existing approved-output ZIP/review/retry workflows; batch links open the real Phase 6 dashboard and selected-approved ZIP exports. Pending/failed/unknown jobs are displayed with their actual status, not invented generated image cards. Approval is a separate decision, not inferred from generation completion. Soft-deleted photos are listed separately without serving their content until restoration.

## Organization and historical integrity

Project folders are the existing `projects` records, extended with `archived`. New `images.library_project_id` is an owner-constrained organization assignment; unassigned is NULL. Moves change only that assignment, not object keys or files. A moved file's original `project_id` remains its immutable **processing context** because source/output composite foreign keys, job leases and pack history rely on it. This distinction is deliberate: moving an image does not rewrite historical executions, instructions, brand snapshots or usage.

New jobs snapshot their source's current library folder in `processing_jobs.library_project_id`; generated images inherit that folder from their existing job's result ID. Thus an original organized into another project can produce new results in that folder while the existing engine continues using its protected processing-context IDs. Existing jobs are backfilled with their historical project, not silently moved. Moving one output does not move/delete its source, siblings or pack. The central project's filtered library shows the current organization; the older project upload page remains the source-processing workspace. Packs and batches retain their historical execution project and are reached through the associated source/output history.

Archiving hides a project from normal library and working-project lists, with an explicit inclusion/restore path. It does not cancel queued work, delete images or revoke historical access. Project deletion is intentionally restricted to projects without organized images **or retained source-context records**. A moved-away original can still keep its source project necessary; archive that project while it holds those dependencies. This phase does not recursively erase a collection or move whole processing families behind the user's back.

## Recovery, cleanup and authorization

Migration `202610280006_library.sql` follows the Phase 6 migration and returns schema version `2026102806`. It adds folder/trash metadata and owner indexes, preserves existing table/usage records, and tightens image SELECT RLS to exclude trashed images. New query/action/project RPCs are service-only and take the session's owner, never a client-supplied owner. Inputs, sort values, IDs, pagination and actions are validated server-side. Bulk mutations validate every member before updating, under the shared processing budget lock. A mixed-owner/missing-ID action rolls back completely.

Library deletion means **30-day recovery**, via `trashed_at`, while the existing private object remains stored and continues consuming quota. Both library actions and the existing DELETE-image endpoint use this recovery path once the new schema is ready. Restoration within the retention window preserves the same image ID/object; expired recovery requests fail honestly. Existing content/download/image-query routes also obey tightened RLS, so trashed images are not accessible by guessing an old ID. New-job insertion checks prevent an upload/preflight race from admitting a trashed source. Active generation or pending/running quality assessment blocks trashing dependencies.

After 30 days, `npm run maintenance` calls `expire_library_trash`, marks eligible expired images `deleting` and then reuses the existing private-storage removal and `complete_deletion` flow. A storage error retains the deleting record for retry; database references are not removed ahead of storage success. Audit/job/usage history is retained according to existing foreign-key semantics, with unavailable photo references nulled where supported. No unrelated generated images are recursively removed. The 30 days is an implemented technical recovery policy, not a claim that legal/retention documents have been published. Operators must schedule maintenance; time alone does not run a sleeping host or erase bytes. Brand assets have their own Phase 5 historical-retention rules and are not secretly purged by photo cleanup.

The existing cookie-authenticated, owner-checked content stream is reused for full downloads. Signed public-object URLs were not introduced because this stream already enforces current authorization and revocation on each request. Gallery Download links exposes individual authorized streams; selected completed/approved archive export remains in the pack/batch workflows, with their existing checksum, decision and byte-limit safeguards.

## Limits and activation

Existing storage/image/project caps, provider budgets, credit accounting and queue behavior are preserved. SQL search is bounded by the current per-account photo quota; no speculative external search service, unsupported capacity or background service was introduced. Thumbnail generation still reads a bounded original on the server; it saves browser bandwidth rather than claiming zero storage reads. Deployments with far larger quotas should benchmark/index search and consider a dedicated private thumbnail cache before raising capacity.

Hosted migrations through Phases 2–7, actual account/worker configuration, API credit and the real provider/hosting throughput checks remain deferred. There is no funded end-to-end provider success claim. Tests use mocks only inside tests; production gallery records, status and file reads are actual Supabase data. No payment checkout or subscriptions.

## Asset-ledger workspace refresh

The Image Library now opens as a data-dense asset ledger with optional gallery and thumbnail-density controls. Supported filename/project search stays prominent; existing advanced filters, sorting and explicit recovery-bin browsing remain server-backed. Loaded counts reflect the returned records rather than an invented library total. Incremental pages preserve existing thumbnail nodes and scroll position; bulk selection is capped at the existing 100-ID API limit.

Project creation, renaming, archive/restore and empty-project deletion are available in a dedicated project drawer. A theater preview loads the selected full image on demand and shows saved version, source, instruction and Brand Studio snapshot data where present. Review links open the existing comparison/decision workflow. Late search/history responses cannot overwrite a newer view; failed reads and writes retain explicit error/retry states.

Original photographs can be staged from the empty canvas or upload dialog and sent sequentially through the existing private upload endpoint. The UI stages up to ten files per operation, retains each upload UUID on uncertain acknowledgement, freezes destination selection in flight and never starts generation. Existing decode validation, ownership, account storage quotas and normalization remain authoritative. Selected downloads use existing private image streams; approved ZIP exports stay in the linked pack/batch workflows. This refresh adds no tag schema, favorites store, external cloud synchronization, new image formats or processing/authorization changes.
